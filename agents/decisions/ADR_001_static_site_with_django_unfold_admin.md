# 🏛️ ADR-001 — Статический сайт + скрытая админка Django/Unfold на Postgres

- **ID решения:** ADR-001
- **Название:** Публичный сайт остается статическим; содержимое редактируется в отдельной закрытой админке Django + Unfold с Postgres и публикуется пересборкой статики
- **Статус:** ACCEPTED (владелец: «Одобряю, этап 1», 2026-11-06)
- **Дата принятия:** 2026-11-06
- **Авторы/Агенты:** Claude Code (Opus 5.5)

---

## 1. Контекст и проблема
- Сейчас все данные (курсы, цены, контакты, филиалы) лежат в `content.js`, а блоки демо (цифры, преподаватели, результаты) — прямо в `index.html`. Любая правка требует программиста и git push.
- Владелец хочет: (1) посетители видят **только статику**; (2) **скрытая** админка для смены содержимого «в нужный момент»; (3) **красивая** современная админка; (4) база **Postgres**. Стандартная админка Django кажется ему устаревшей.
- Ограничения проекта: сайт — HTML/CSS/Vanilla JS, генератор `build.mjs`, Caddy в Docker на Railway, 49 тестов + CI; Dockerfile/Caddyfile/railway.json/content.js защищены baseline-хэшами.

## 2. Рассмотренные альтернативы
1. **Django-сайт целиком (SSR) + стандартная админка.** Плюс: одна система. Минусы: публичная часть перестает быть статикой (против требования), устаревший вид админки.
2. **Directus поверх Postgres.** Плюсы: красивая админка почти без кода. Минусы: ограниченная кастомизация, лицензия BSL с порогом оборота, логика валидации — вне нашего кода.
3. **Payload CMS (Next.js).** Плюсы: современная, MIT. Минусы: тяжелый Next.js-сервис, больше кода на TypeScript, второй стек рядом с Python-инструментами проекта.
4. **Django + Unfold как отдельный закрытый сервис, публикация = пересборка статики (выбрано).** Плюсы: современный вид (Unfold 0.110.1, MIT, Django 5.2–6.1, Python ≥3.12), полный контроль и Python-валидация, публичный сайт не меняет природу. Минусы: больше кода, чем у Directus; второй сервис и Postgres на Railway (доп. расходы).
5. **Оставить как есть** (правки через агента/git). Плюс: ноль инфраструктуры. Минус: не решает задачу владельца.

## 3. Принятое решение (предлагается)
- Публичный сервис `site` (Caddy + статика) **не меняется по природе**: собирается из `content.js` генератором `build.mjs`.
- Новый закрытый сервис `cms` (Django 6.1 + Unfold, Postgres на Railway) хранит данные и по кнопке «Опубликовать»:
  1) валидирует данные (те же правила, что `validateContent`);
  2) экспортирует `content.js` и оптимизированные фото;
  3) запускает `node build.mjs` (Node в образе cms) и получает `index.html`;
  4) одним коммитом через GitHub API отправляет `content.js`, `index.html`, `assets/uploads/**` в `main`;
  5) GitHub Actions прогоняет тесты; Railway с «Wait for CI» деплоит `site` только при зеленом CI.
- `content.js` остается в git как опубликованная копия (история, откат, резерв).

## 4. Последствия
- **Позитивные:** посетители видят только статику (быстро, без поверхности атаки); админка красивая и на русском; каждая публикация — коммит (история и откат через git); тесты продолжают охранять сайт.
- **Негативные / Риски:** +2 сервиса на Railway (Postgres, cms) — ежемесячные расходы; токен GitHub с правом записи в репозиторий хранится в cms; публикация занимает несколько минут (CI + деплой); «Wait for CI» на Railway, по отзывам сообщества, иногда пропускает деплой.
- **План смягчения рисков:** fine-grained токен только на этот репозиторий и только Contents; секреты только в переменных Railway, не в чате и не в git; скрытый путь админки, django-axes против перебора, HTTPS-cookie, noindex; в админке видно состояние CI/деплоя последней публикации и есть инструкция ручного redeploy; ежедневные бэкапы Postgres Railway + git-история `content.js`.
